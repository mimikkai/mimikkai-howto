# Progress bar in browser emulator did not animate (stale-timer race + discrete jumps)

**Date:** 2026-06-11 00:22
**Files:** lib/cases/price-search/steps/StepProcessing.tsx, lib/cases/threads-comments/steps/StepProcessing.tsx, lib/cases/scheduler.ts (new), lib/cases/scheduler.test.ts (new)
**Severity:** medium

## Problem

In the browser-emulator inside `StepProcessing`, the horizontal progress bar (used in Google-loading, marketplace-loading, threads-loading, tab-switching phases) appeared to either not animate or jump straight to 100%. The CSS class `transition-all duration-300` was already present, so the symptom was not a missing animation primitive.

## Root Cause

Two interacting bugs:

1. **Stale-timer race in `schedule()`.** The helper was a bare `setTimeout(fn, ms)` that did not track or clear its timer id, and re-checked only `isRunningRef.current` (which becomes `true` again on resume). When the user paused mid-phase and resumed, the previous wave of `setTimeout`s stayed alive. On resume they would fire — possibly firing the "30 → 100 at t=5000" timer before the new "0 → 30 at t=3500" timer — so the new wave of state writes landed in the wrong order. The CSS transition then saw a single render-time jump from the stale value to 100 and had nothing to animate.

2. **Discrete `loadingProgress` values without interpolation.** The Google phase was driven by `setBrowser` writing `loadingProgress: 0` → `30` → `100` in three `setTimeout` calls. Even without the race, the CSS transition only had ~300 ms to ease between two points — visually the bar looked like it teleported. There was no RAF-driven tween between the discrete check-points.

A symmetric issue existed in `setInterval` for typing animations: stale intervals continued to write into `typedQuery` after resume, producing flicker.

## Solution

- Extracted scheduler concerns into `lib/cases/scheduler.ts` exposing a `createScheduler()` factory with:
  - `schedule(fn, ms)` — tracked setTimeout with auto-cleanup of its id from the set
  - `trackTimer(id)` / `trackInterval(id)` — for timers/intervals created outside `schedule` (e.g. `flashUrl` timeout, table-flash reset, typing intervals)
  - `tweenProgress(from, to, durationMs, onUpdate, onDone?)` — RAF-based tween with quadratic ease-in-out; auto-skips when `isStale(myRunId)`
  - `cancelAll()` — clears all pending timers, intervals, and rafs
  - `nextRunId()` / `isStale(myRunId)` — run-id guard so any callback from a previous pause/resume cycle is a no-op
- `processNext` now:
  - Bumps the run-id at entry
  - Wraps every scheduled callback in a `scheduler.isStale` + `isRunningRef` guard
  - Replaces the discrete `loadingProgress: N` writes with `scheduler.tweenProgress(...)` calls spanning the actual phase duration
  - Tracks all `setInterval`s for typing and removes them on `cancelAll`
- `handlePause` calls `scheduler.cancelAll()` — no more stale callbacks
- `handleStart` registers its initial 300 ms kick-off timer through the scheduler
- `useEffect` cleanup on unmount also calls `cancelAll` to avoid leaks when the user navigates away

The same fix was applied symmetrically to `lib/cases/threads-comments/steps/StepProcessing.tsx`.

Added 6 unit tests in `lib/cases/scheduler.test.ts` covering: monotonic tween, `durationMs=0` shortcut, `cancelAll` mid-tween, `schedule` + `cancelAll`, `nextRunId` / `isStale`, `trackTimer` cancellation. Tests use a self-rolled `installRafMock()` that patches `requestAnimationFrame` and `performance.now()` so the scheduler is fully deterministic without browser APIs.

## Prevention

- **Never call `setTimeout` / `setInterval` in React state-driven flows without a tracker Set + cancel function.** This pattern (call → save id → cancel on pause/unmount) is the only way to avoid stale-timer races in any "play / pause / resume" UX.
- **For any value that drives a CSS animation, prefer RAF interpolation between discrete check-points over discrete jumps.** A jump from 0 to 100 has nothing to ease; ten 1% bumps per frame give a smooth animation.
- **Treat `runId` as a guard, not just an ID.** Every `setTimeout` callback in a multi-stage orchestrator should compare `myRunId === runIdRef.current` and short-circuit if stale. This is the same idea as React 18's effect-cleanup, applied to imperative scheduling.
- **Make a shared `createScheduler()` for any scenario that needs to schedule work.** Now any new scenario in `lib/cases/<slug>/` can just `const scheduler = useRef(createScheduler(...))` and use `scheduler.schedule / tweenProgress / cancelAll` instead of inventing its own.
- **When writing tests for browser-only APIs (`requestAnimationFrame`, `performance.now`), install a mock that returns a virtual clock and a virtual id-space.** Otherwise tests are flaky and depend on real wall-clock time.
