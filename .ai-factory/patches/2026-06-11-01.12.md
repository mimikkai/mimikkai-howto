# Animate new browser tabs in price-search emulator

**Date:** 2026-06-11 01:12
**Files:** app/globals.css, lib/cases/price-search/steps/StepProcessing.tsx
**Severity:** low

## Problem

In the price-search browser-emulator, when a new tab is added to the tab strip (at 7500ms when Google → first marketplace; at 13500ms when switching to the second marketplace for price comparison), the new tab appeared instantly with no entrance animation. The user could not visually track the "new tab opened" event, which made the multi-step comparison feel less polished.

## Root Cause

The per-tab `<div>` (`lib/cases/price-search/steps/StepProcessing.tsx:949-961`) had no `animate-*` class, no `@keyframes` was defined for tab appearance, and `key={i}` (array index as key) means React mounts only the newly added tab as a fresh DOM node. Without any entrance animation, a freshly mounted node is rendered in its final state — invisible transition.

The codebase already had a similar pattern for table rows (`@keyframes rowSlideIn` + `.row-animate-in` utility in `app/globals.css`), so the fix follows an established convention rather than introducing a new approach.

Note: `lib/cases/threads-comments/steps/StepProcessing.tsx` was inspected and intentionally **not** modified — the Threads scenario models a single-page flow (no `tabs` field in its `BrowserState`); there is no multi-tab concept to animate.

## Solution

Three small changes, mirroring the existing `rowSlideIn` pattern:

1. **`app/globals.css`** — added `@keyframes tabEnter` (320 ms ease-out: opacity 0→1, translateX 8px → -1px → 0, scale 0.95 → 1.01 → 1, with `transform-origin: right center` so the new tab appears to slide in from the right of the strip). Added `.tab-animate-in` utility class. Added `@media (prefers-reduced-motion: reduce)` override that disables both `.tab-animate-in` and `.row-animate-in` for users with the accessibility setting on.

2. **`lib/cases/price-search/steps/StepProcessing.tsx:969`** — added `tab-animate-in` to the per-tab `<div>` className. Because `key={i}` is the array index, React mounts only the new (last) element, so the keyframe fires only on the freshly added tab — exactly the desired UX.

3. **Logging.** Added a `useEffect` watching `browser.tabs.length` (line 263 area) that logs `[price-search:processing] tab added` with `{ prev, next, title, url }` whenever the array grows. Useful in dev to confirm the right moment was reached.

The existing `transition-all duration-200` on the per-tab div (which animates the active/inactive border + background swap) continues to work and does not conflict — `transition-all` operates on `border-color` / `background` / `color` while `tabEnter` operates on `transform` / `opacity`.

## Prevention

- **For any list whose items can be added over time (rows, tabs, cards, list items), pair a stable CSS utility class with a `@keyframes` from the start.** It costs almost nothing to define, and the UX benefit of "you can see the new thing arrive" is huge. The pattern is now established twice in the project (`row-animate-in` for table rows, `tab-animate-in` for browser tabs).
- **When designing `useEffect` over a state that has both identity-preserving and identity-replacing changes, gate by structural diffs, not by content.** Here we track `tabs.length` (structural) instead of deep-equal of the array — cheaper, deterministic, and avoids spurious logs.
- **`prefers-reduced-motion` is a one-liner that matters.** Always pair entrance animations with the media-query override. Users with vestibular disorders or motion sensitivity will appreciate it.
- **Don't reach for animation libraries for entrance transitions.** A 5-line `@keyframes` plus a one-line utility class is enough for 90% of UX motions. Framer Motion is appropriate only when gestures, layout transitions, or staggered orchestration are required.
- **Use `transform-origin` deliberately.** Setting `transform-origin: right center` on a tab that slides in from the right is what makes it feel like the tab "pops out" of the strip's right edge instead of growing from the centre. The same trick is reusable for sidebars, dropdowns, and notification cards.
